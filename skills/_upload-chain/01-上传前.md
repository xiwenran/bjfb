## U1：扫描合成图文件夹

```bash
python3 ~/zhifa/scripts/skill_upload.py scan <合成图文件夹>              # 单主题
python3 ~/zhifa/scripts/skill_upload.py scan-many <topic_dir...> --output <scan.json>   # 多主题（必用）
```

脚本会打印人类可读摘要（每个主题组 + 包含的笔记 + 是否已有封面），并把原始 JSON 写入显式路径（含 `noteKey`、`folderPath`、`images`、`videos` 数组），后续步骤只引用这个显式路径。

**多主题目录必须用 `scan-many`**：禁止为了「省事」逐个主题调用 `scan` 后复用 `/tmp/zhifa_scan_result.json`；这会互相覆盖，导致少传、漏传或把整主题误当成单篇。

**扫描后必须列出识别结果让用户确认**：打印扫描到的主题组列表，让用户核对数量和名称是否符合预期，再继续。

**三层目录口径（重要）**：合成图根目录若是 `内容分组 / PPT主题 / 笔记子文件夹` 三层结构，真实笔记是第三层「笔记子文件夹」，不是第二层 PPT 主题，也不是图片数量。第二层 PPT 主题只写入 `pptTopic`，不算篇数。封面可在笔记子文件夹内，也可在 PPT 主题根目录共享，不能因缺少共享封面把 PPT 主题误判成一篇笔记。

**混合结构必须停问**：若某个 PPT 主题目录根部有直接内容图/视频，同时下级子文件夹也有素材，扫描必须阻断并询问用户「根部素材是否也算一篇笔记，还是只发布下级子文件夹」，不得静默猜测。

**常见干扰项**：合成图文件夹下可能存在非主题文件夹（如 `逐字稿/`、`封面/`、`备份/` 等），scan 会把它们也识别为主题组。列出扫描结果时，若发现疑似非笔记文件夹（没有数字编号子目录、名称明显不像课题），**必须停下追问用户是否排除，不得凭名称推断自行过滤**，不要自动纳入上传。

**数量不一致时**停下来问用户：
> 「扫描发现 N 个主题组：[列出名称]，但你提供了 M 张封面。请告诉我哪张封面对应哪组，或者确认是否有组不需要封面。」

等用户明确确认后再继续 U2。

**错误处理**：返回空列表 → 检查上一步合成图是否生成正确，停下报告，不静默跳过。

## U1.5：教师产品资产库关联账本闸门（入口 A）

> 目的：已手工做好的笔记（合成图目录）写入飞书前必须先在教师产品资产库「笔记关联账本」落一笔归属状态——`linked`（关联到某个 product_id）或 `unlinked_note`（明确暂未归属，仍允许继续发布）。飞书记录一旦写入即禁止程序化删改（飞书记录红线见 SKILL.md「注意事项」），所以这道闸必须卡在 U1 扫描之后、U2/U3 之前，不让未登记的笔记假装已归属产品。

**登记前先确认合成图目录已定稿（CRITICAL）**：账本按 `folderPath` 绝对路径认笔记，**目录一旦改名，已登记的记录全部失效、必须重登**。所以模板子目录的命名要在登记之前定下来，登记之后不许再重命名、移动或重新合成覆盖。若确实需要改名，改完必须重新跑一遍本步骤，不能沿用旧登记。

对 U1 `scan-many` 产出的 `<scan.json>` 里每个笔记的 `folderPath`（已是绝对路径），查询账本：

```bash
cd ~/teacher/codex-skills/teacher-product-assets && \
python3 -m teacher_product_assets.cli note-list \
  --db ~/teacher/publish-library/.asset-db/assets.sqlite3
```

把返回 JSON 数组的 `note_dir`（账本存的是 `folderPath` 的 canonical 绝对路径）与 scan.json 里每个 `folderPath` 逐一比对：

- 命中（`link_type` 为 `linked` 或 `unlinked_note`）→ 放行，继续 U2。
- 未命中 → 先跑自动匹配推荐，再问用户，不得跳过推荐步骤直接空手问：

```bash
cd ~/teacher/codex-skills/teacher-product-assets && \
python3 -m teacher_product_assets.cli note-match \
  --db ~/teacher/publish-library/.asset-db/assets.sqlite3 \
  --note-dir "<folderPath>"
```

拿到结果后，**先看 `result_state` 字段**，按它分五种情况问用户，不得代用户拍板：
  - **`recommended`（唯一 high 置信度推荐）** → 带着推荐问：「`<folderPath>` 还没登记归属，自动匹配推荐关联到 `<product_code>`（<推荐依据>），是否确认关联到该产品？」用户确认后执行 `note-register --product-code`。
  - **`multiple_candidates`（多个候选）** → 列出全部候选（product_code + 依据）供用户选择，或选择先登记为 `unlinked_note`。
  - **`no_candidates`（零候选）** → 建议登记为 `unlinked_note`：「`<folderPath>` 自动匹配未找到候选，建议先登记为 unlinked_note 允许继续发布，之后再补关联。」
  - **`relocated_match`（这份笔记已登记过，但登记在另一个路径下）** → **不要按零候选处理、不要重新 `note-register`**——重新登记会让同一份笔记在账本里出现两条，重复计数。结果里的 `existing_note_dir` 是它此前登记的路径。带着信息问用户：「`<folderPath>` 的内容与账本里 `<existing_note_dir>` 那条登记是同一份（按笔记图内容指纹核对），应该是上一轮归档时把目录移走了。是否确认执行 `note-relocate` 把账本更新到当前路径？」用户确认后执行：
    ```bash
    cd ~/teacher/codex-skills/teacher-product-assets && \
    python3 -m teacher_product_assets.cli note-relocate \
      --db ~/teacher/publish-library/.asset-db/assets.sqlite3 \
      --candidate "<folderPath>" --actor "<执行人>" --reason "<为什么搬迁>"
    ```
    若 `note-relocate` 把该候选计入 `skipped` 并说明「旧登记路径仍然存在」，说明这是**内容被复制了一份**而不是搬家，两个路径同时存在。此时停下问用户哪一份是正主，不要自行选一个，也不要绕过去重新登记。
  - **`path_missing`（路径在磁盘上不存在，账本里也查不到）** → 这**不是命令报错**，是正常返回的状态，不适用下方 Fail-closed。先核对 `<folderPath>` 有没有写错；确认路径无误却仍是这个状态，说明这批笔记的目录已经不在了，停下报告，不要继续往 U2 走。

无论哪种情况，最终登记动作只能在用户明确确认后执行，不得凭推荐结果自动登记。不得跳过闸门直接进入 U2。

登记命令（用户选择后执行）：

```bash
# 已知道产品归属（含用户确认的自动匹配推荐）
cd ~/teacher/codex-skills/teacher-product-assets && \
python3 -m teacher_product_assets.cli note-register \
  --db ~/teacher/publish-library/.asset-db/assets.sqlite3 \
  --note-dir "<folderPath>" --product-code "<product_code>" --actor "zhifa-upload"

# 暂不知道产品归属，允许继续发布
cd ~/teacher/codex-skills/teacher-product-assets && \
python3 -m teacher_product_assets.cli note-register \
  --db ~/teacher/publish-library/.asset-db/assets.sqlite3 \
  --note-dir "<folderPath>" --unlinked --actor "zhifa-upload"
```

事后补关联（笔记发布后确认了归属，`unlinked_note → linked`，留历史不覆盖）：

```bash
cd ~/teacher/codex-skills/teacher-product-assets && \
python3 -m teacher_product_assets.cli note-relink \
  --db ~/teacher/publish-library/.asset-db/assets.sqlite3 \
  --note-dir "<folderPath>" --product-code "<product_code>" --reason "<人工核实说明>"
```

**Fail-closed**：teacher-product-assets 的 db 文件不存在、`note-list`/`note-match` 命令报错、或 JSON 输出解析失败时，一律停下报告，不得视为「未登记=允许放行」，也不得把命令报错当成「零候选」处理。

反过来也要分清：`path_missing` 与 `relocated_match` 是 `note-match` **正常返回的状态**（退出码 0、JSON 完整），不是命令报错，不适用本条 Fail-closed，按上面五分支各自的处理方式走。判据是退出码与 JSON 能否解析，不是「结果看着不对劲」。

## U2：放置封面图

**事前定位（CRITICAL — 不可跳过）**：进入本 U 前主会话必须粘贴本节标题及第一句原文：「读取 U1 产出的 `<scan.json>`，取出每个 topic group 下所有笔记的 `folderPath` 字段（已是绝对路径）。**优先使用共享执行层自动下发封面**：`python3 ~/zhifa/scripts/skill_upload.py materialize-covers <scan.json>`」。

**U1 scan 摘要的 ⚠️ 缺封面警告允许是误报**：scan 摘要只检查笔记**子文件夹内**的 `0*.jpg`。当封面放在**主题根目录**（如 `主题/0.jpg`），摘要会一律报「⚠️ 缺封面」。这种情况下**正确反射动作是直接跑 `materialize-covers` 把根目录封面下发到子目录**，而**不是转头问用户「封面在哪」**——这是 `materialize-covers` 专门为之解决的场景。

**反射动作硬规则**：看到 scan 摘要里有 ⚠️ 缺封面警告时，主会话**禁止**直接进入「问用户封面位置」，必须先：
1. `ls <主题根目录>` 检查是否已有 `0*.jpg` / `0*.png` 文件
2. 有 → 跑 `materialize-covers`，重扫确认
3. 主题根目录和 `folderPath` 向上路径都没有任何主序号 `0*` 文件 → 默认该批图文素材不需要单独封面，记录说明后继续
4. 只有用户明确说「有封面/要放封面」但路径或文件缺失时，才追问封面完整路径

跳过此自检直接问用户 = 跳读 U2（CLAUDE.md「跳读 SKILL.md 自作主张」的同根错误）。

> ⚠️ **封面放置层级**：如果本批素材有 `0*` 封面，封面图必须放在**每篇笔记的模板子文件夹内**（如 `主题/1/0.jpg`、`主题/2/0.jpg`），不是放在主题文件夹根目录（`主题/0.jpg`）。`materialize-covers` 命令的作用就是把主题根目录的封面自动复制到所有子文件夹。没有任何 `0*` 封面的图文素材按「无单独封面」继续，不补、不问、不移动。

读取 U1 产出的 `<scan.json>`，取出每个 topic group 下所有笔记的 `folderPath` 字段（已是绝对路径）。优先使用共享执行层自动下发封面：

```bash
python3 ~/zhifa/scripts/skill_upload.py materialize-covers <scan.json>
```

有封面下发时，必须重新运行 `scan-many`，用新的 `<scan_after_covers.json>` 继续后续步骤，避免 records 里保留改名前或补封面前的旧图片路径。没有 `0*` 封面可下发时，继续使用原扫描结果。

**单张封面**（该组只提供一张图）：

```bash
cp "<封面图路径>" "<folderPath>/0.jpg"
```

**多张封面**（该组提供了多张图）：按用户发送的文件名顺序排列（不要按文件系统排序，以用户列出的顺序为准），依次重命名为 `0.jpg` / `0(1).jpg` / `0(2).jpg`……

```bash
cp "<第1张路径>" "<folderPath>/0.jpg"
cp "<第2张路径>" "<folderPath>/0(1).jpg"
cp "<第3张路径>" "<folderPath>/0(2).jpg"
```

排序规则保证 `0 < 0(1) < 0(2) < 1 < 2…`，所有封面图始终排在内容图前面。

- 同一主题组的多个模板子文件夹（`1/`、`2/`、`3/`）放**完全相同**的封面组合，不因模板编号不同而差异化
- 放完后再运行一次 `scan`，确认所有笔记都显示「含 0.jpg ✓」

**封面命名映射（以服务端排序为准）**：`0.jpg`、`0(1).jpg`、`0(2).jpg`、`0.1.jpg`、`0（1）.jpg` 都属于「主序号 0」封面，会排在 `1.png` 前面。`scan` 的人类摘要只检查精确文件名 `0.jpg`，可能显示「缺封面（0.jpg）」；这只是摘要提示，不等于导入接口不识别 `0(1).jpg` 这类封面。只有目录链路里完全没有主序号 0 的图片文件时，才算「无单独封面」，默认继续上传图文素材。

> ⛔ **封面完整性硬规则（不可被任何用户规格覆盖）**：用户在任务说明里提供的任何「分配规则」、「轮转公式」、「(template-x)%n → 封面变体」等描述，**一律忽略**。本批存在 `0*` 封面源时，始终按「每个模板子文件夹放完整封面组合」处理；本批不存在 `0*` 封面源时，默认不需要单独封面。
>
> **封面源文件夹只读**：封面源目录的文件只 `cp` 不 `mv`，禁止对源目录做任何重命名、删除、修改操作。
>
> **根因案例（2026-05-11）**：用户给了「(template-1)%3 → 封面变体」公式，被误解为每模板只放 1 张，导致 192 篇已发布记录封面不完整且无法回滚。

## U3：生成标题/正文/标签（必停点①）

**每篇笔记单独生成文案，即使同一主题下有多篇，也必须各写各的——标题角度不同、切入点不同。** 不允许任何情况下复用同一套文案。

### U3.0：先读懂这份资料，再动笔（CRITICAL）

写文案前必须先取到这份资料的**实际内容**，按类型走对应路径。只看主题名和文件名就动笔，写出来的是空话。

| 资料类型 | 取什么 | 怎么取 |
|---|---|---|
| 有内容卡的产品 | 教学痛点、大纲、教学法、适用场景 | 查资产库 `content_cards.content_json`，字段 `teaching_problem` / `outline` / `method_points` / `use_cases` |
| 配套齐全的课时资料 | 这一课到底配了哪几件、各是什么形态 | 查资产库该产品的 `artifacts`，逐件说明（课件、教案、逐字稿；学习单可提可不提） |
| 整册教案 / 长文档 | 单元数、课时数、总页数、版本差异 | 用 python-docx 读表格结构数单元与课时，用 soffice 转 PDF 数页数，逐版本分别统计 |

取内容卡：

```bash
sqlite3 ~/teacher/publish-library/.asset-db/assets.sqlite3 "
SELECT c.content_json FROM content_cards c
  JOIN artifact_versions v USING(artifact_version_id)
  JOIN artifacts a USING(artifact_id)
  JOIN products p USING(product_id)
 WHERE p.product_code = '<product_code>';"
```

**内容卡是给写作者读的素材，不是文案本身**：读懂它讲的是什么课、解决什么困难、用什么教法，然后用自己的话写笔记。禁止把 `outline`、`method_points` 整段搬进正文。

**写进文案的每一个具体特征都必须回原始素材核实（CRITICAL）**。内容卡由程序从课件自动提取，属线索不属事实；页数、课时数、单元构成、是否含练习题、是否含某个栏目，一律以原始文件为准。核实不了的特征就不写，**不允许推测性补全**（例：没数过页数不写页数；没在课件里看到练习题不写「配练习」；没确认单元清单不写「某某单元全覆盖」）。

**逐字稿是老师最看重的配套**，有就在正文里点出来并说明它的用处；不要用「四件套」这类打包说法代替逐一说明。

**文案必须在上传之前完成**：`title` 和 `tags` 预填进 records JSON，知发收到预填标题后跳过自身 AI 生成。**禁止**先上传空标题的记录再事后补写——事后补写需要额外脚本，且容易遗漏。

**完整写作规范（CRITICAL — 字面注入，不许只写路径）**：

执行本 U 前，主会话**必须**先用 `sed -n '/^const SYSTEM_PROMPT/,/;$/p' ~/zhifa/src/ai-writer.js`（按标记提取，不依赖行号，SYSTEM_PROMPT 增删行后命令依然完整）把 SYSTEM_PROMPT 字面文本提取出来（2026-07 已重构为原则驱动+搜索流量优先，废弃旧的双层结构/钩子菜单/公式体系），把内容**完整粘贴**到本步骤的工作上下文里（核心目标 + 三条原则 + 正文写法 + 正文硬边界 + 标签写法 + 硬边界 + 输出格式示例全部）。不允许只写「请参考路径」——主会话自己也好、派子代理也好，所有用到这套规则的位置都必须看到字面文本。

理由：已踩坑——派子代理时只给路径让「自行读取」，子代理跳读导致标题写偏 3 轮。字面注入是唯一可靠路径。

生成标题前必须向用户明确写出：`标题规则来源：已读取 ~/zhifa/src/ai-writer.js 的 SYSTEM_PROMPT`。没写出这句，视为标题规则未进入本轮工作上下文。

**正文（description）必须撰写，不允许留空**。按 SYSTEM_PROMPT「正文写法」撰写：首行展开完整搜索词长句，中间逐行列实际覆盖内容，末行可选（无内容点直接收尾，不为收句凑话）；禁写「图片即为完整内容/完整内容见图/内容按图整理/翻图查看/完整版」等完整性话术（发布图只是部分素材）；JSON 字符串里用 `\n` 分行（不要写真实回车）。

**正文写法（2026-08-04 换新，字面来源同样是 SYSTEM_PROMPT「正文写法」，与上面的字面注入要求同步生效）**：不分段带 emoji，不套「困难/怎么做/适用场景」三段公式。开头一句说清是什么、难在哪；中间按资料实际结构走，三步设计写三步、两道关写两道关；结尾有真东西说一句，没有就停，结尾那句只能来自资料原话或对资料结构的观察。句子之间不搭桥、不写过渡句；语序可以不捋顺、允许绕回来；长短拉开，该展开的掰碎说，次要的一句带过；允许絮叨和口头词（其实/还挺/根本/才），允许放一两句跟资料无关的废话（孤零零占一行）；用大白话动词（用/改/有/就/能），专业表述保留原样；句号能少则少，段末不加句号，并列项用空格或顿号，不用引号/冒号/破折号/分号，课文名正文里不加书名号。段落 2–4 行为主，整篇 6–8 段，用逗号连着走，一段说完一件事再换行。**正文字数 300–500 字（机械校验硬指标已放宽到 50–500，写作目标口径按 300–500 执行）**，禁止使用经历词（如"我的体会""备课时发现""亲测"）、无法验证的承诺（如"照着讲就行""拿来就能用"）、联系方式（微信号/QQ号/手机号/二维码），提到教案/逐字稿/学习单/板书时必须是该产品资产库里真有的配套件，查不到会被打回——这四条与标题/标签规则一样由服务端 `validateGenerated` 机械校验。

**不写读者身份预设**：不写「新老师」「新手教师」这类假定使用者经验水平的说法，用资料本身的用处代替（例：写「逐字稿把每一步该说的话写出来了，可以直接照着讲」，不写「新老师不用从零开始」）。

### 生成流程

1. 读取 `~/zhifa/src/ai-writer.js` 的 `SYSTEM_PROMPT`
2. **同一主题下多篇笔记必须一次性批量生成 N 个角度不同的标题**（N = 该主题下笔记篇数），不允许逐篇独立生成。批量生成要求：
   - 主干句式不重复（不允许改一两个词就算「角度不同」）
   - 先列出该主题下所有笔记编号，再一次给出完整 N 条标题候选
3. 每篇笔记单独生成：先按语义判断这份资料是什么（课件/教学设计/知识点总结/家长会/班会……不预设分类清单），再判断目标老师会搜什么词，标题以搜索关键词为主体组织成自然流畅的一句话，写 2–3 个候选标题
4. 正文按 SYSTEM_PROMPT「正文写法」撰写：首行展开完整搜索词长句，中间逐行列实际覆盖内容，末行可选（无内容点直接收尾）；禁写完整性/引导翻图话术（见 SYSTEM_PROMPT「正文硬边界」）；禁用词/敏感词同标题共用同一份清单（见 SYSTEM_PROMPT「硬边界」）
5. 按 SYSTEM_PROMPT「标签写法」组装标签；飞书「标签」字段提取搜索词标签，**每个标签带 `#` 前缀**（如 `#经典常谈 #马说`），少而准不凑数

**标题生成后必须逐一检查以下规则，不通过则重写**：
- 字数 10-20 字（所有字符全部计入，《》每个符号计 1 字、emoji 计 1 字，与程序逐字符计数一致；`skill_upload.py` 的 Title length 检查下限是 10，写 8、9 字会被 dry-run 打回）
- **标题最多带 1 个 emoji（可以不带），要带就从白名单里选**：📌 🔥 ✅ 💡 ✨ 📝。这与 `skill_upload.py` 的机械校验一致；两处若出现分歧，以机械校验为准并回头修本文档
- **年级词禁用**：七年级 / 八年级 / 九年级 / 七上 / 七下 / 八上 / 八下 / 九上 / 九下
- **课文名/书名不允许缩写**，原名直接使用（《钢铁是怎样炼成的》不得缩写为《钢铁》）；标题超字数时优先压缩其他搜索词要素，不动课文名
- 标题只能用主题和图片文件名里真实存在的信息，不得编造属性（课时划分、板书、可打印、教案、习题答案、使用场景等）；不堆砌、不营销、不写情绪钩子
- 同批次任意两篇标题除课名/单元外不得雷同，不套用同一句式模板

**正文生成后检查**：是否撰写（非空）、是否按首行/中间结构展开（末行可选、不强制）、无「图片即为完整内容/完整内容见图/翻图查看/按图整理」等完整性话术、无引导互动词/平台敏感词。

每条标题+正文自检通过后才进入预览环节。

**fallback 调 `/api/ai-writing/generate` 时的校验（CRITICAL）**：主会话手写失败时才 fallback。`/api/ai-writing/generate` 服务端已内置机械校验（`validateGenerated`）+ 1 次自动重试：不合规会先反馈违规项重新生成一次，重试后仍不合规则直接抛错，不会静默放行不合规内容。fallback 成功返回 `title/description/tags` 后，主会话仍需按 SYSTEM_PROMPT 硬边界复核一遍字数/标签数量/违规项是否自洽，且违规项必须为 `无` 才能进入预览确认；不能手填一列后跳过复核。**fallback 报错时，如实告知用户失败原因，不得手动编造内容绕过校验。**

**预览必停点①**：生成后展示预览，等用户说「确认」后才继续。预览不得只展示标题，必须包含「标题 / 字数 / 违规项」三列；违规项为 `无` 才能进入确认：

```
📋 内容预览（请确认后说「确认」继续）

── 组1：草船借箭的历史背景与战争智慧 ──
| 候选 | 标题 | 字数 | 违规项 |
|---|---|---:|---|
| A | …… | 18 | 无 |
| B | …… | 19 | 无 |
正文：首行搜索词展开句\n中间逐行列内容（末行可选，不写完整性话术）
标签：#历史故事 / #三国 / #战争智慧

── 组2：赤壁之战：以少胜多的经典战例 ──
…
```

文案确认后，把每篇的 `title` / `description` / `tags` 写进 `content.json`（供 U4 `build-records` 使用），进入 `02-上传.md`。
