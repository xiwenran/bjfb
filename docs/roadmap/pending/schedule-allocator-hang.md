# 排期职责重划：求解拆出软件，软件只做校验

> 2026-07-31 诊断 + 方案定稿，未改任何代码（当时其他会话正在使用软件）。
> 方案已随讨论演进：初版为「修好服务端求解器」，定稿改为「把求解拆出软件」。下文保留诊断，方案以本版为准。

## 现象

素材导入页调排期时，知发 App 整体无响应（窗口、菜单栏全卡），不只是排期按钮转圈。约束密集的批次（例：21 主题 × 8 模板 = 168 个 noteKey，8 账号 × 7 时段）必现。请求被服务端掐断后 App 也不会自行恢复。

## 根因

### 表层一：排期同步跑在 Electron 主进程

- `src/electron-main.js:4` 直接 `require('./server.js')` 并 `startServer`，HTTP 服务与 Electron 主进程同线程。
- `src/server.js:1095` 同步调用 `allocateImportSchedule`，回溯期间事件循环被完全占满。
- HTTP 连接被掐断不会终止同步计算，主线程继续被占——这是卡死后不自行恢复的原因。

### 表层二：算法是无启发式的全局 DFS 回溯

- `src/scheduler-allocator.js:303` `search()` 为纯深度优先回溯，无 MRV、无约束传播。
- 分支因子 ≈ 段内候选分钟数 × 段数 × 候选笔记数（上述批次为上千级），深度 = 任务数（数十至上百）。
- commit `5fe8029` 只加了 `MAX_PLACEMENT_ATTEMPTS = 2000000` 次预算并消除内层重复计算，**未更换算法**，因此约束一密仍然爆炸。
- 该预算的单次尝试成本并非常数：`:365` 与 `:368` 在每次回溯撤销时各跑一遍 O(schedule 长度) 的 `schedule.some(...)` 线性扫描。

### 真正的根因：职责错配

服务端排期被要求「在一次 HTTP 请求内、无人介入地、一次性给出全局解」。但排期天然需要业务判断——实测出问题的批次是「A 组 8 个账号只有 7 个主题」，在 `auto_space` 下第 8 个账号必然与某账号同时段撞主题；此时该少发一篇、还是放宽错峰、还是调整时间窗，是人的决策，不是算法能替代的。

把需要判断的过程塞进同步黑盒，**无论算法怎么优化都是错的**。且 DFS 恰在这类「接近无解」的实例上耗时最长，用户还无法区分「无解」与「搜不动」。

## 定稿方案：求解拆出软件，软件只做校验

### 1. 软件端：删求解器，改为校验器（fail-closed）

- 删除 `src/scheduler-allocator.js` 的求解逻辑（422 行）。
- `/api/import/schedule` 从「求解并返回 schedule」改为「**接收** schedule + 全量校验 + 不合规整批拒绝」。
- 校验为 O(n) 一遍扫描，毫秒级，同步跑也不会卡；因此 `utilityProcess` 化、超时、取消入口**均不再需要**。
- 校验必须覆盖全部硬约束，一条不过整批拒收，禁止部分接收：
  1. 同平台同账号任意两条间隔 ≥ 361 分钟
  2. 全批次分钟全局唯一（并纳入 `existingReservations` 已有排期）
  3. 同平台内 noteKey 不重复
  4. 同账号内 template 不重复
  5. `auto_space` 时同 storeGroup 同 topicKey 跨账号间隔 ≥ 361 分钟
- 报错必须结构化：指出具体是哪两条记录、违反哪条约束、差多少分钟。

**这一条是防线，不可省。** 求解拆出去后若软件照单全收，硬约束就只剩外部脚本的自觉，防线从机械层退回文字层——即项目已记录的「机制幻觉」坑。校验器是唯一权威闸门。

### 2. 脚本端：独立排期脚本

- 新增 `scripts/schedule_allocator.py`（与既有 `scripts/skill_upload.py` 同语言同目录，skill 直接调用），纯函数、可测试、不进 Electron 打包路径。
- 采用构造式排期，不搜索：
  1. 构造完整 noteKey 池（主题 × 模板）。
  2. 账号 i 在时段 t 取池中 `(i + t) % N` 位置 → 同账号跨时段不重复、同时段跨账号不重复。
  3. 每个时段窗口按本时段任务数均分为互不重叠的段，段内各取一分钟 → 全局分钟唯一自动成立；占用池纳入 `existingReservations`，跨批不撞。
  4. 同账号相邻时段间隔本身已大于 361 分钟。
- 复杂度 O(n)，一次成型。允许慢、允许打印中间过程、允许多轮迭代、允许 AI 参与「8 账号 7 主题怎么分」这类判断。
- 产出 `schedule.json`（沿用既有契约 `{topic, topicKey, noteKey, platform, account, storeGroup, publishTime}`）后交软件校验，通过再走 `build-records`。

### 3. 前端：本次不动（原「去掉 UI 排期入口」一条已撤销）

施工前清点发现：`/api/import/schedule` 的**唯一调用方是 `scripts/skill_upload.py:1115`，前端从未调用该接口**（`grep -rn "import/schedule" public/` 无命中）。

前端 `public/index.html:2992` 的 `allocateTimesByWindows` 是素材导入页自带的另一套时间分配逻辑，与服务端 allocator 相互独立、仍在正常使用。原方案「清理前端排期入口」基于错误前提（提问时未先核实调用关系），若照做会误删在用功能，故撤销。**本次改动不触及 `public/`。**

### 4. 约束配置单一来源

`MIN_SAME_ACCOUNT_INTERVAL_MINUTES = 361` 目前硬编码在 `scheduler-allocator.js:3`。抽为一份 JSON 配置，校验器（JS）与排期脚本（Python）读同一份，避免两边漂移。

注：校验与求解是两份独立实现（JS / Python），这不是缺陷而是交叉验证——但**权威永远是校验器**，脚本与校验器判断冲突时以校验器为准。

## 相比「修好求解器」的收益

| 维度 | 修求解器（初版方案） | 拆出去（定稿） |
|---|---|---|
| 代码量 | 重写 422 行 + 新增 Dinic 最大流 + 局部修正 | 删 422 行，新增约 80 行校验器 |
| 架构改造 | 必须做 `utilityProcess` 化 + 超时 + 取消 | 不需要，校验毫秒级 |
| 改排期策略 | commit → dist:mac → 覆盖安装 → 核对 hash | 改脚本即可，不重打包 |
| 人可否介入 | 否，同步黑盒 | 可，离线多轮迭代 |
| 无解 vs 搜不动 | 需专门设计才能区分 | 天然区分：脚本构造式无解即真无解 |

初版方案中的 `utilityProcess` 化、三阶段解耦、Dinic 最大流、有界局部修正**全部作废**，不再实施。

## 自然消解的遗留问题

- `spread-minutes`（跨批撞分钟的事后补丁）可退役：脚本侧全局占用池已保证跨批不撞。
- `:365` / `:368` 的线性扫描随求解器删除一起消失。
- seed 复算性：语义转移到脚本侧，同 seed 同输入仍同解；服务端不再承担复算责任。

1. 先补校验器的回归测试，五条硬约束逐条构造正反用例（**先写，作为验收基准**）。

6. 同步 `skills/_upload-chain/02-上传.md` 的排期流程描述。
7. 真实批次端到端跑通（含一次故意不合规的输入，验证校验器确实拒收）。
